## 2026-03-14 | phase3-phase4-trust-errors | Shared TLS certificate failure contract for HTTP and Win32 internet APIs
- Decision: `src/net/http.rs` now distinguishes TLS failure classes instead of collapsing certificate and transcript faults into `TlsNotSupported` or generic connection failure. The HTTP client emits separate classes for handshake failure, transcript decode failure, certificate date invalid, hostname mismatch, invalid CA, invalid certificate, and revoked certificate.
- Decision: `src/win32.rs` now maps those HTTP/TLS failure classes onto stable WinINet/WinHTTP-style `ERROR_INTERNET_*` codes, so the Win32 bridge reports date/CN/CA/revoked/decode failures through different last-error values instead of flattening them into `12045` or `12029`.
- Decision: `src/shell/mod.rs` now surfaces the same TLS failure classes in `http`, `wget`, `curl`, and `net status`, so shell diagnostics no longer hide certificate date/CN/CA/revoked/decode failures behind raw debug output.
- Rationale: Faz 3 and Faz 4 both needed the same exactness slice: security failures had to become behavioral contracts rather than a single opaque HTTPS failure bucket. Without that split, the network stack and Win32 internet facade could not claim truthful failure semantics.
- Tradeoffs: The new mapping sharpens error classes, but it is still a first-pass trust model. Full Schannel/browser-grade chain policy, proxy/cache/session behavior, and revocation-fetch policy remain outside this slice.
- Evidence: Windows SDK `wininet.h` constants from `C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\um\wininet.h`; unit tests in `src/net/http.rs` and `src/win32.rs`.
- Supersedes: The prior state where certificate parse, hostname, issuer, and revocation failures all surfaced as `TlsNotSupported` or generic connect failure on the Win32 bridge.
- Next validation: Run targeted host-side tests for the new TLS/error mapping slice, then extend the same contract into shell-facing HTTPS diagnostics and deeper Schannel-grade policy checks.

## 2026-03-12 | win32/loader-sockets | Real PE TLS callback invocation and wider ws2_32 ABI surface
- Decision: `src/pe_loader.rs` now promotes TLS from mere `.tls` template allocation to a runtime contract: the loader captures `IMAGE_DIRECTORY_ENTRY_TLS`, records callback VAs and the TLS index slot in `PeTlsContext`, zero-initializes the loader index cell, and invokes TLS callbacks with `DLL_PROCESS_ATTACH` before transferring control to the PE entry point. In parallel, `src/win32_abi.rs` widens the real Winsock surface by exporting `WSASocketA/W`, `sendto`, `recvfrom`, `getsockopt`, `setsockopt`, `htons`/`ntohs`, `htonl`/`ntohl`, and `inet_addr`; `resolve_module_dispatch()` now also returns concrete `advapi32`, `shell32`, and `msvcrt` exports instead of restricting itself to `kernel32/user32/gdi32`.
- Rationale: The largest remaining “looks like Windows, behaves unlike Windows” gap was the loader/network seam. PE processes with TLS callbacks were skipping loader-managed attach work entirely, and Winsock clients probing beyond the narrow `socket/connect/send/recv` core saw imports resolve to nothing despite the underlying echOS socket layer already supporting `sendto/recvfrom/getsockopt/setsockopt`.
- Tradeoffs: TLS callback support is process-attach only; thread-attach, SEH unwind metadata, and loader notifications beyond `DLL_PROCESS_ATTACH` remain outside this slice. Winsock breadth increased, but the implementation still maps only IPv4 and a constrained socket-option set onto echOS net primitives.
- Evidence: `cargo build --target x86_64-unknown-uefi`; `.\.qoder\skills\echos-architect\scripts\echos_gate.ps1 -Paths src\pe_loader.rs,src\win32_abi.rs,src\win32.rs,docs\agent\decision-log.md`.
- Supersedes: The previous state where `init_tls()` only copied `.tls` bytes without honoring `IMAGE_TLS_DIRECTORY` callbacks, and where `resolve_ws2_32_symbol()` exposed only the narrow stream-socket core despite richer underlying transport primitives.
- Next validation: Run PE samples that depend on TLS callbacks and Winsock datagram/options APIs, then extend the loader to thread-attach and exception-directory semantics once app compatibility proves it necessary.

## 2026-03-11 | gui/cursor | Cursor frozen at (24,24) — VelvetGlove never flushes damage to framebuffer
- Decision: Added `self.shell.client.present_frame()` at the tail of `DesktopSession::tick()` in `src/gfx/velvet_glove.rs`. Also aligned all three initial cursor positions: `EchDisplay::cursor_position` and `EchInput::last_cursor` both changed from `(24,24)` / `(0,0)` to `(640,400)` to match `MOUSE_X`/`MOUSE_Y` defaults.
- Rationale: The VelvetGlove main loop (`session.tick() + hlt`) correctly processes IRQ12 bytes via `poll_input → drain_raw_input → handle_packet → PointerMove → update_cursor`, updating `cursor_position` and marking `DamageTracker` regions. However, `EchDisplay::run_service()` (the only caller of `present()`) is spawned at `Priority::Low` and never receives CPU time because the VelvetGlove loop never calls `schedule()` or `preemptible_schedule()`. The `hlt` instruction suspends only until the next interrupt; the timer ISR sets `need_resched` but cannot call `schedule()` while `HardIRQGuard` is held (`in_hardirq() == true` → `preemptible() == false`). After the ISR returns, execution resumes inside `session.tick()` which has no preemption point. The net result: damage accumulates in `DamageTracker` indefinitely; the cursor stays frozen at the value painted during `ech_display::init()` (a single `process_command(DisplayCommand::Present)` call). `present()` already exits cheaply (`damage.lock().take().is_empty()` path) on quiet frames, so calling it on every tick adds negligible overhead.
- Tradeoffs: `present_frame()` acquires several `spin::Mutex` guards on every tick even when there is no damage. On a 100 Hz timer the amortized cost is one `Mutex::lock + is_empty` check per 10 ms — acceptable. The deeper fix (giving `EchDisplay::run_service` actual CPU time via a yield point in the VelvetGlove loop) is deferred; `preemptible_schedule()` could be added later once task-switch correctness is validated under the preempt model.
- Evidence: Static analysis of `scheduler::tick()` (called under `HardIRQGuard`) confirms `schedule()` is unreachable from the timer ISR; `EchDisplay::run_service` has no other activation path. Cursor initial-position mismatch confirmed: `MOUSE_X/Y = (640,400)`, `cursor_position = (24,24)`, `last_cursor = (0,0)` — on the first event `raw_delta = (640,400)` which after `filter_pointer_delta` clamps to `(256,256)`.
- Supersedes: none.
- Next validation: Boot in QEMU (`run_qemu.ps1`), verify cursor moves with mouse and starts near screen centre. Check serial log for `[DESKTOP] session bootstrap` markers reaching `success`. Optionally add `preemptible_schedule()` call in tick loop and confirm `ech_display` task gets scheduled via ghost event log.
